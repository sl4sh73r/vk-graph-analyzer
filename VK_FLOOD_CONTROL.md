# VK Flood Control — Решение проблемы

## ⚠️ ВАЖНО: Проверьте сначала двойной запрос OAuth!

**Самая частая причина Flood control — двойной вызов OAuth callback из-за React StrictMode.**

Если в логах backend вы видите:

```
Requesting token from VK ID OAuth...
Requesting token from VK ID OAuth...  ← ДВА РАЗА!
```

То проблема **НЕ в VK API**, а в вашем коде! 

**Читайте:** [REACT_STRICTMODE_OAUTH.md](./REACT_STRICTMODE_OAUTH.md)

---

## Предварительные требования

Перед началом убедитесь, что:

1. ✅ **ngrok запущен** и настроен HTTPS туннель (см. [README.md](./README.md) и [VK_ID_SETUP.md](./VK_ID_SETUP.md))
2. ✅ VK ID приложение настроено с правильным **Redirect URI** (через ngrok домен)
3. ✅ OAuth защита от двойных запросов работает (useRef + backend deduplication)
4. ✅ Backend и frontend запущены

Только после этого можно диагностировать и решать проблемы с VK API rate limits.

## Проблема

После авторизации через VK ID при попытке построить граф вы сразу получаете ошибку:

```
VK API Error [friends.get]: { error_code: 9, error_msg: 'Flood control' }
```

### Почему это происходит?

VK API отслеживает частоту запросов **не только с момента запуска вашего сервера**, но и учитывает историю запросов за последние 10-15 минут от:
- Вашего IP-адреса
- Вашего токена доступа
- Комбинации метод+параметры

Если вы:
- Тестировали приложение несколько раз подряд
- Перезапускали сервер и снова делали запросы
- Использовали другие приложения/скрипты с тем же токеном

...то VK "помнит" это и блокирует новые запросы с кодом 9 (Flood control).

## Решение 1: Начальная задержка (Initial Cooldown)

### Что делает?

Перед первым запросом `friends.get` (если нет кеша) приложение **подождёт** заданное количество секунд. Это даёт VK время "забыть" предыдущие запросы.

### Как включить?

В файле `backend/.env` добавьте:

```properties
VK_INITIAL_COOLDOWN_SEC=60
```

**Значения:**
- `0` — без задержки (по умолчанию)
- `60` — подождать 1 минуту перед первым запросом (рекомендуется)
- `90` — подождать 1.5 минуты (если 60 секунд не помогло)
- `120` — подождать 2 минуты (максимально безопасно)

### Когда применяется?

- **Только** если список друзей **не найден в кеше**
- **Только** при первом запросе после запуска сервера
- При повторных запросах (если данные в кеше) — задержки не будет

### Пример работы

```
🔍 Building graph for user 403298662 with depth 1...
⏳ Initial VK cooldown: waiting 60s before first friends.get...
[прогресс: "Ожидание перед запросом: 60с"]
... через 60 секунд ...
✅ [friends.get успешно выполнен]
```

## Решение 2: Кеширование (уже работает)

### Что делает?

После успешного получения списка друзей приложение сохраняет его:
- **В памяти** (на время работы сервера)
- **На диске** (файл `backend/.cache/friends/{userId}.json`, TTL 6 часов)

При следующем запросе данные берутся из кеша → **VK API не вызывается** → Flood control не срабатывает.

### Где кеш?

```
backend/.cache/friends/
  └── 403298662.json  # список друзей для пользователя 403298662
```

### Когда кеш обновляется?

- Каждые **6 часов** (автоматически)
- При удалении файла вручную
- При перезапуске сервера (кеш в памяти очищается, но файлы остаются)

## Решение 3: Слайдер скорости запросов (Throttling)

### Что делает?

В интерфейсе приложения есть слайдер **"Скорость запросов к VK"** (300-3000 мс):
- По умолчанию: **1200 мс** между запросами
- Минимум: 300 мс (риск Flood control)
- Максимум: 3000 мс (безопасно, но медленно)

### Как использовать?

1. Если получаете Flood control часто → увеличьте до **2000-3000 мс**
2. Если всё работает стабильно → можете уменьшить до **800-1000 мс**

### Где настроить?

В левой панели приложения (Sidebar) → раздел **"Скорость запросов к VK"**.

## Решение 4: Экспоненциальный Backoff (уже работает)

### Что делает?

При получении Flood control (код 9) приложение:
1. Ждёт ~2 секунды и повторяет запрос
2. Если снова ошибка → ждёт ~4 секунды
3. Если снова ошибка → ждёт ~8 секунд
4. ...до 8 попыток с увеличивающейся задержкой
5. Финальный cooldown 30 секунд
6. Последняя попытка

### Пример лога

```
⏳ VK rate limit (code 9). Backoff 1934ms (attempt 1/8)
⏳ VK rate limit (code 9). Backoff 4098ms (attempt 2/8)
⏳ VK rate limit (code 9). Backoff 7074ms (attempt 3/8)
...
🧊 Flood control persists. Cooldown 30000ms then final retry...
```

## Рекомендации

### Если Flood control появляется сразу после авторизации:

1. ✅ Установите `VK_INITIAL_COOLDOWN_SEC=60` в `.env`
2. ✅ Перезапустите backend: `npm run dev` в `backend/`
3. ✅ Подождите 60 секунд после нажатия "Построить граф"
4. ✅ Первый запрос пройдёт успешно, данные закешируются
5. ✅ Все последующие запросы будут использовать кеш → Flood control не будет

### Если Flood control появляется при расширении графа:

1. ✅ Увеличьте слайдер **"Скорость запросов"** до 2000-3000 мс
2. ✅ Уменьшите **количество друзей для анализа** (maxFriends) до 5-10
3. ✅ Используйте **глубину = 1** вместо 2-3

### Как избежать Flood control в будущем:

- ✅ Не делайте много запросов подряд во время разработки
- ✅ Используйте кеш (он автоматический)
- ✅ Увеличьте минимальный интервал между запросами в `.env`
- ✅ Дайте VK "отдохнуть" 1-2 минуты между тестами

## Проверка настроек

### 1. Проверьте `.env`:

```sh
cat backend/.env | grep VK_INITIAL_COOLDOWN_SEC
```

Должно быть: `VK_INITIAL_COOLDOWN_SEC=60`

### 2. Перезапустите backend:

```sh
cd backend
npm run dev
```

### 3. Проверьте лог при построении графа:

Должна появиться строка:

```
⏳ Initial VK cooldown: waiting 60s before first friends.get...
```

### 4. Дождитесь окончания задержки

Прогресс-бар покажет: **"Ожидание перед запросом: 60с"**

### 5. Проверьте успешность запроса

После задержки должна появиться строка:

```
👥 Depth=1: friends ids total = 123
```

**Без** ошибки `Flood control`.

## Альтернатива: используйте Service Key

Если у вас есть **VK Service Key** (из настроек приложения на vk.com):

1. Добавьте в `.env`:
   ```
   VK_SERVICE_KEY=ваш_service_key
   ```

2. Service Key имеет более высокий лимит запросов (300 запросов в 5 минут)
3. Но не может получить закрытые друзья пользователя

## Итого

**Лучшая комбинация для работы без Flood control:**

```properties
# backend/.env
VK_INITIAL_COOLDOWN_SEC=60        # Задержка перед первым запросом
```

+ **Слайдер в UI:** 1200-2000 мс  
+ **Кеш:** включён по умолчанию (TTL 6 часов)  
+ **Backoff:** включён по умолчанию (до 8 попыток)

Это гарантирует стабильную работу даже при частых запросах.
